ReqBot Future Improvements and Experiment Backlog
================================================================

Purpose
----------------------------------------------------------------
This file is a parking lot for useful ideas that should not be lost.
It is not a phase tracker, release plan, or source of truth for current
implementation status.

Use this document for:

- good ideas that are out of scope for the current work package
- experiments worth trying before committing to a feature
- cleanup items that are real but not urgent
- decisions we do not want to re-debate without new evidence

When an item becomes active work, move the detailed requirements into the
appropriate phase or work-package document. Keep this file short enough that
it remains useful.

ACTIVE BACKLOG

1. Step C concurrency
   Explore a small worker pool for LLM extraction. This could reduce long ingest
   times, but it must be tested carefully because local Ollama/GPU setups may
   become unstable with concurrent generation requests.

   Experiment gate:
   - measurable ingest-time improvement
   - no increase in malformed or partial LLM output
   - graceful behavior on single-GPU  machines

2. Streaming write in Step A
   For very large PDFs, write page records incrementally instead of buffering all
   pages in memory. Current documents do not appear to require this, but it is a
   useful scalability hardening item.

3. Ollama finish_reason / token metadata
   Investigate whether Ollama response metadata can detect truncation more
   reliably than JSON parse failure alone.

4. Remove duplicate profile vocabulary constants
   Step C and Step D.5 still keep module-level VALID_DOMAIN_TAGS and
   VALID_REQUIREMENT_TYPES constants that mirror profiles/cybersecurity.json.
   They remain useful for compatibility today, but they are a second source of
   truth. Consider deriving fallback defaults from core.profiles when the profile
   plumbing is stable enough.

5. [RESOLVED — Phase 34, WP-34.1] Profile-based skip-section filtering — docling-only gap
   Was: profiles/*.json's skip_sections field only took effect on the docling
   path; the legacy pymupdf/pdfplumber chunking path had no section hierarchy
   and silently no-op'd on it. WP-34.1 removed the legacy path entirely --
   docling is now the only ingestion backend, so skip_sections always applies.
   No remaining gap; see docs/PHASE34_REQUIREMENTS.md.

6. Optional LLM-backed audit question generation
   Phase 21 intentionally leaves audit_question blank. A future opt-in feature
   may use an LLM to generate human-friendly audit questions, but it must not be
   default behavior.

   Guardrails:
   - explicit user flag or UI toggle
   - source_quote remains primary
   - no invented obligations
   - blank is better than an unsupported rephrase
   - generated questions should be marked as generated text

11. [DEPRIORITIZED — 2026-07-27] Checklist assessor-note preservation on regeneration
    Considered for Phase 31 and dropped, not deferred again by default: no real user is currently
    doing the edit-notes-then-regenerate workflow this protects, and this item had already been
    delayed several times waiting for one. Revisit only if that usage pattern actually starts
    happening (Tyler, 2026-07-27) -- the problem description below stays accurate if it does.

    Running generate() for a document that was already exported and annotated
    will silently reset assessor_notes and status to their initial values
    ("" / "not-started"). Any assessor work done against the exported CSV or
    JSON is lost unless the user saved the file.

    A future enhancement should detect a prior checklist export for the same
    doc_key and merge assessor_notes and status back in by checklist_item_id
    before writing output. Deterministic IDs make this possible without
    requiring the user to manage filenames.

    Design constraint:
    - merge must be opt-in or clearly documented, not silent
    - IDs are stable across re-runs for the same requirement_id, so a
      re-ingested document that produces the same requirement_ids will
      correctly re-associate assessor notes

23. [SPIKE COMPLETE — Phase 33, WP-33.3] Actionability self-verification for
    extracted requirements
    The spike confirmed a real, sizable problem (37.5% of a random 40-record
    corpus sample), but it is NOT the single "too vague" pattern this item
    originally assumed -- it decomposes into 5 distinct root causes, only one
    of which is genuine vagueness. Full writeup, real examples, and the A/B
    prompt-test methodology (run twice for stability, results were NOT
    stable -- that instability is itself part of the finding):
    `docs/PHASE33_REQUIREMENTS.md`'s WP-33.3 Findings. Reusable test script +
    both runs' raw output: `eval/actionability_spike.py`,
    `eval/spike_results/wp_33_3/report.md`.

    The five causes, largest by count first (count and danger are different
    axes -- do not conflate "largest" with "most concerning" below):
    1. Reference/bibliography-list entries mis-extracted as requirements
       (17.5%, largest by count), often with Step D.5 fabricating a
       description not grounded in the quote. Prompt-wording fix tested
       twice -- reduced the count both times but never to zero, and the two
       runs disagreed by ~4x on the size of the improvement (16->14, then
       15->6) -- too unstable to credit as a real fix.
    2. Genuine vagueness/administrative meta-statements (12.5%, second-
       largest by count) -- the originally-assumed pattern.
    3. Truncated/fragment quotes (list headers ending in ":") paired with a
       Step D.5 description that fabricates the missing content (2.5% by
       count, but the MOST DANGEROUS of the five -- a confident-sounding
       description with no real source). Prompt-wording fix tested twice --
       zero effect in run 1, worse (added a second fragment) in run 2.
    4. Background/definitional prose extracted despite no obligation
       language (2.5%).
    5. Non-obligation form/questionnaire content mis-extracted as a
       requirement (2.5%) -- e.g. a "State how often is X..." questionnaire
       prompt, not an obligation on an organization at all.

    Prompt wording also has a reproducible NEW-fabrication risk: on two
    independent runs, the revised (longer) prompt made the model regurgitate
    its own few-shot examples verbatim on a chunk that normally extracts
    cleanly -- word-for-word identical fabricated text both times. WP-32.1's
    existing Step D grounding check already catches this pattern today
    (a regurgitated example won't fuzzy-match a chunk that never contained
    it), which is a good validation of why that check exists, but it means
    editing Step C's prompt is not a free/low-risk lever on this model.

    Recommended fix, next time this is picked up (do not assume a single
    is_verifiable classifier -- these need different mechanisms):
    - Category 1: a chunk-level or Step D structural filter for
      citation-list-shaped chunks/quotes.
    - Category 3: a minimum-predicate / no-trailing-colon structural check
      in Step D, alongside the existing errata_change_entry check.
    - Categories 1 and 3 both involve Step D.5 fabricating description
      content ungrounded in the quote it was given, so a description-
      grounding check is worth prioritizing -- but it is NOT a direct
      extension of WP-32.1's existing check. That check does fuzzy
      substring/partial-ratio matching between a verbatim source_quote and
      its verbatim source chunk -- valid because both sides are meant to be
      the same literal text. description is an intentional paraphrase
      (ENRICH_BATCH_PROMPT_TEMPLATE/ENRICH_SINGLE_PROMPT_TEMPLATE explicitly
      ask for "one precise sentence summarizing," not verbatim text), so a
      real, faithful summary would legitimately score low on a literal
      substring match -- reusing the same mechanism would reject good
      enrichments alongside fabricated ones. This needs a claim/entailment
      check (do the specific facts named in the description actually appear
      in the quote), which is more design work than a one-line "extend the
      existing check" -- scope it as its own investigation.
    - Category 2 (genuine vagueness) is the lowest priority of the five --
      not because it's the smallest (it's the second-largest by count), but
      because Step C prompt changes are the riskiest lever demonstrated
      above (regression risk, reproduced twice), and this category is the
      one most inherently suited to a prompt-only fix, which this spike
      showed doesn't work reliably on this model. May not be worth a
      dedicated fix at all.

    Connects to item 6 above (audit_question generation): both are an extra
    per-requirement LLM judgment made after extraction. If both get built,
    do them as one combined Step D.5 call, not two separate ingest-time LLM
    passes.

26. Impact analysis via MCP -- diff two versions of a document, surface corpus
    dependents (ChatGPT strategy conversation + Claude follow-up, 2026-07-29;
    full discussion at reqbot-agent-docs/reqbot/references/ReqbotConvo.md)
    Pitch: a regulation or STIG updates, and instead of manually diffing old
    vs. new and hunting for what else in the corpus depended on it, ReqBot
    answers both inside the same MCP conversation.

    What already exists toward this: compare_documents(doc_id_1, doc_id_2,
    topic) already has an "exact" mode keyed on source_ref, returning which
    control IDs appear in doc1 only, doc2 only, or both -- most of a document
    diff already, just scoped to one topic/control per call. trace_requirement
    (requirement_id) already returns "cross-framework matches sharing the
    same source_ref in other documents" -- a real, if narrow, dependency
    signal.

    Gaps, not yet built:
    - No exhaustive sweep. Nothing diffs every source_ref in doc1 against
      doc2 in one call -- the caller has to already know which topics to
      compare. Building this is mostly a batch wrapper: iterate every
      distinct source_ref in the old doc, run compare_documents' exact mode
      against the new doc, roll up added/removed/reworded (text-similarity
      on source_quote for shared source_ref pairs -- the same kind of check
      WP-32.1 already built for grounding).
    - No document version identity. Re-ingesting a new STIG revision just
      creates another doc_key next to the old one; nothing records "this
      supersedes that." Fine for a manually-pointed compare_documents call,
      but means the assistant can't proactively flag that a newer version
      exists.
    - Cross-reference is control-ID-literal only. trace_requirement's
      cross-framework matching only catches cases where the same source_ref
      string appears elsewhere -- a policy discussing a control conceptually
      without citing its literal ID won't surface. Closing this needs either
      explicit citation extraction during Step C/D, or an approximate
      semantic fallback (weaker, more false positives/negatives).

    Do first if picked up: the exhaustive-diff wrapper (smallest, reuses
    existing tools) before tackling version identity or citation-aware
    cross-referencing.

27. Multi-document concept mapping, N-way (same source conversation as item 26)
    "These six controls, three STIG findings, and two internal policies all
    relate to the same concept." compare_documents already does this
    pairwise (two doc_ids at a time), and trace_requirement's cross-framework
    matching starts from one already-known requirement_id. Neither discovers
    a cluster across the whole corpus starting from a free-text concept.
    Would need a new tool: given a topic, return every source_ref cluster
    across all indexed documents that maps to it, not two documents at a
    time.

28. Gap identification against a user-supplied document (same source
    conversation as item 26)
    "Your SSP discusses AC-2 but never addresses account review frequency" --
    checking a user's own document (SSP, policy) for coverage against the
    corpus of extracted requirements. None of the current MCP tools take an
    ad-hoc external document as input; this needs its own extraction/matching
    pass (does each of a control's sub-requirements have a corresponding
    statement in the user's document, not just a mention of the control ID)
    rather than reusing existing retrieval as-is. More novel than items
    26-27 -- scope as its own investigation before committing to a WP.

29. Cross-document consistency / contradiction detection (same source
    conversation as item 26)
    Example: a policy says "MFA required everywhere," the SSP says "MFA only
    for privileged accounts." compare_documents can already show that two
    documents both touch a topic (ref_groups), but detecting an actual
    contradiction is a judgment task, not a presence/absence check -- needs
    an LLM comparison step over matched passages, not just retrieval. The
    most novel of items 26-29; scope after the others land, since it's the
    least like anything that exists today.

    Deliberately not added alongside 26-29: "evidence suggestions" (canned
    typical-evidence-per-control knowledge, e.g. "AC-2 usually uses an AD
    export, an HR onboarding SOP, quarterly review logs"). map_evidence
    already covers the corpus-grounded version of this (builds an evidence
    pack per topic from indexed source material) -- the remaining gap is a
    general knowledge layer independent of any ingested document, which is a
    different and much fuzzier thing to build, not an extension of what's
    here.

30. Docling acronym/glossary list entries sometimes parse with no enclosing
    heading (found during WP-34.3's heading-vocabulary survey, Phase 34)
    NIST.SP.800-171r3.pdf's acronym list (e.g. "CFR", "CISA", "CUI") gets
    docling-parsed as standalone, parentless headings -- section_title_path
    is just ["CFR"], with no "Acronyms"/"Abbreviations" ancestor at all. This
    isn't a skip_sections vocabulary gap (WP-34.3's territory): there's no
    parent heading text to match against, so no amount of vocabulary tuning
    fixes it. It's a HybridChunker/section_parser structural-parsing
    limitation for this specific list-of-bolded-terms layout. Not fixed as
    part of WP-34.3 (out of scope -- that WP is profile vocabulary, not
    chunking logic). Worth a real look if it turns out to recur across other
    documents' acronym lists, since it means those entries currently reach
    Step C unfiltered as candidate requirements.

33. [PARTIALLY RESOLVED -- Phase 36, docs/PHASE36_REQUIREMENTS.md: WP-36.1
    (exact-match short-circuit) merged 2026-07-31 -- all 4 known exact-match
    false positives confirmed eliminated with no change to fabricated-catch
    rate, live-verified against real MiniCheck. WP-36.2 (threshold re-sweep,
    now that exact matches no longer reach the model) still pending.]
    MiniCheck's entailment score already-measurably rejects a
    description that is a verbatim (word-for-word identical) copy of its own
    source_quote -- 80% of WP-35.2's own reported false-positive rate, not
    an edge case (found during WP-35.5's integration run, Phase 35, against
    a real fresh ingest of `afpd_17-1.pdf`; corrected after Codex review on
    PR #170 -- the first version of this item wrongly claimed the shape was
    invisible to calibration)
    Step D.6's entailment check (WP-35.2/35.4) rejected 5/64 requirements'
    descriptions in a live full-pipeline run -- every one of the 5 has
    `description` byte-identical to `source_quote` (e.g.
    `"Participate in cyberspace governance forums."` -> the exact same text
    as its own description), with `support_prob` scores of 0.6782-0.8442,
    below the 0.85 threshold. A verbatim copy cannot be "fabricated" in any
    meaningful sense -- there's zero new content -- so this is a real
    MiniCheck calibration weakness specifically for very short premise/
    hypothesis pairs, not a description-fabrication catch. WP-35.3's
    modality check correctly did not flag any of these (nothing obligatory
    was invented), confirming the two checks' specificity is working as
    designed; this is purely an entailment-threshold false-positive.
    **This is not a newly-discovered blind spot -- checking directly shows
    it was already the dominant driver of WP-35.2's own reported false-
    positive rate.** 77 of the 92 `wp_35_1_harvest` faithful records in
    `eval/gold_description_grounding.jsonl` (84%) are exact
    `description == source_quote` matches (the faithful holdout is a random
    sample of everything neither harvester heuristic flags, not gated by
    the heuristics themselves -- an exact match trivially passes into it).
    `eval/spike_results/wp_35_2/results.json`'s `scored_records` show 4 of
    the 5 false positives WP-35.2's sweep reported at threshold 0.85 are
    this exact pattern (`REQ-938435202cf9` 0.8473, `REQ-8105d9acb410`
    0.2766, `REQ-fd23f59eb131` 0.2507, `REQ-69fe659699bb` 0.3312 -- only
    `REQ-7b7cbb7ef5b7` is a real paraphrase false positive). WP-35.5's
    integration run reproduced an already-known, already-measured weakness,
    not a new one -- given it's 84% of the faithful calibration set, this
    plausibly affects a large share of real production traffic too, not a
    rare shape.
    Separately notable: per `ENRICH_SINGLE_PROMPT_TEMPLATE`'s own
    instructions, Step D.5 is supposed to return `description: ""` when
    source text is "self-explanatory" rather than echo it verbatim -- some
    fraction of these 77 records suggest that instruction isn't always
    followed, which is part of *why* the shape is so common, but is a
    separate, pre-existing Step D.5 prompt-following question, not something
    WP-35.5 is scoped to investigate.
    Not fixed here -- WP-35.5 is an integration gate, not a new failure-mode
    investigation (its own Non-Goals), and this is a pre-existing, already-
    accepted calibration cost (WP-35.2 never claimed 0% false positives),
    not a regression WP-35.4/35.5 introduced. Worth a real look given its
    now-quantified scale, before treating the 0.85 threshold as anything but
    provisional (already the documented stance,
    `eval/spike_results/wp_35_2/report.md`) -- either add a cheap
    exact/near-exact-match short-circuit ("description == source_quote ->
    always grounded, skip the model") ahead of the MiniCheck call, which
    would have eliminated 4 of WP-35.2's original 5 false positives outright
    and could allow a lower, more effective threshold to be chosen once
    exact matches no longer need to go through the model at all.

RETRIEVAL EXPERIMENTS
================================================================

These are quality experiments, not guaranteed product work.

1. Reranker spike
   Add a local reranker stage after RRF fusion for precision improvement.
   Prior planning exists but was deferred before execution -- see
   archive/PHASE15_EXTENSION_RETRIEVAL_HARDENING.md (WP-15.5) for the fuller
   architecture writeup (candidate pool sizing, reject-if criteria).

   Insertion point -- corrected after Codex review on PR #140 caught this
   stated wrong: core/ask.py's retrieve() is NOT a single shared choke point.
   It only backs the Ask/Search path (ask_service.py -> CLI `ask`,
   SearchView, and MCP's search tool). Evidence (services/evidence_service.py)
   and Compare (services/compare_service.py) each run their own independent
   dense+sparse+RRF query_points() call -- neither goes through retrieve() at
   all. So there are three separate hybrid-retrieval implementations today,
   and a reranker added only to retrieve() covers Ask/Search/CLI/MCP-search
   but NOT Evidence or Compare (including MCP's evidence tool, which calls
   evidence_service.build() the same way the GUI does).

   Evidence's copy is also missing pieces retrieve() already has: no HyDE
   leg, no min_score filtering, and no headroom past top_k for a reranker to
   reorder within (limit=top_k directly, no separate fusion_limit) --
   giving it that headroom is its own prerequisite, separate from adding the
   reranker itself.

   Before reranking ships, decide: centralize the three retrieval paths into
   one shared implementation first (this already violates the "no separate
   logic for CLI/GUI/API/MCP" guardrail below), or add reranking to each
   path deliberately and accept the duplication. Don't assume fixing one
   path covers the others.

   Blocking prerequisite: there is no retrieval-precision eval set today.
   eval/eval_harness.py measures Step C extraction precision/recall (gold
   chunk -> extracted requirements), not query -> ranked-result relevance.
   The archived PHASE15 plan assumed a "Phase 15 evaluation query set"
   existed as a success-criteria reference, but that phase was deferred
   before one was ever built. Build a small query -> relevant-requirement_ids
   gold set (reusing the existing gold_eval_chunks hand-labeling pattern)
   before any Precision@5 number can mean anything.

   Secondary implementation notes:
   - retrieve()'s fusion_limit is only widened past top_k when min_score > 0
     (max(top_k*3, 50) if min_score > 0 else top_k) -- the "retrieve 40-50
     candidates" headroom a reranker needs isn't guaranteed unconditionally
     yet; decouple candidate-pool size from min_score.
   - min_score is calibrated to RRF's score scale today. If reranker scores
     later become the confidence signal (see corrective retrieval gate
     below), that threshold needs recalibrating, not reusing as-is.

   Candidate approaches:
   - FlashRank for fast local reranking (cheapest first spike)
   - cross-encoder for higher quality with more cost

   Gate:
   - Precision@5 improvement on the new eval set
   - no regression on known good queries
   - acceptable latency on target hardware
   - do not make default unless it clears the gate

2. Multi-vector retrieval
   Index multiple semantic surfaces per requirement, such as description and
   source_quote, to improve recall across different query styles.

   Critical rule:
   Collapse to unique requirement_id before reranking or display so one
   requirement cannot crowd out the result set.

3. HyPE / hypothetical question indexing (separate from HyDE)
   Pre-generate likely user questions for each requirement at ingest time and
   index those as an additional retrieval surface.

   This may improve query-time recall, but it adds generated text to the index
   and should be clearly separated from source-grounded fields.

4. Corrective retrieval gate
   If retrieval confidence is weak, retry once with a targeted rewrite or
   alternate retrieval strategy, then surface a low-confidence warning if the
   result is still weak.

   Depends on having calibrated reranking or confidence signals.

5. Raw-context search as an explicit MCP tool (distinct from item 4)
   grc_context is indexed but only used today for context around existing
   requirement hits (core/ask.py's retrieve_context_chunks) -- it isn't
   exposed as a general "search the raw ingested text" capability. Primary
   use case: an MCP agent gets curated requirements first, then deliberately
   wants to search grc_context as a follow-up, rather than ReqBot's UI
   inventing a weak-confidence fallback path.

   This is a different thing from item 4 above: item 4 is an automatic
   system-triggered retry, this is an agent-triggered deliberate tool call.
   Keep them separate -- item 4 still needs a trustworthy confidence signal
   (reranker scores, see item 1) before it's safe to trigger automatically;
   this one doesn't, since a human/agent is deciding to reach for it.

   Do first:
   - Add an MCP-facing raw-context search tool.
   - Compare grc_requirements vs. direct grc_context search on representative
     queries to know what it's actually good for.
   - Clearly label grc_context results as lower-confidence than curated
     requirements.

================================================================
BACKBURNER
================================================================

1. OSCAL output
   OSCAL is a NIST-standardized machine-readable format for compliance data.
   It may be useful for integration with tools such as Archer or ServiceNow.

   Keep on backburner until a concrete integration target exists. Do not make
   OSCAL the default checklist format.

2. OCR support
   Useful if low-text page detection proves scanned PDFs are common. This should
   be a separate design decision because OCR can add heavy dependencies and
   operational complexity.

3. Authentication / multi-user hosting
   ReqBot currently fits self-hosted and local/air-gapped use well. Auth and
   multi-user hosting should be planned only when there is a deployment target
   that needs it.


================================================================
DECISIONS AND GUARDRAILS
================================================================

1. Keep description and source_quote
   They serve different purposes. source_quote is provenance; description is a
   readable normalized summary.

2. Do not use deterministic requirement_id hashing as the only ID strategy
   Requirement IDs can be assigned during normalization. Checklist item IDs may
   be deterministic from requirement IDs.

3. Do not lower num_predict casually
   The extraction path has already seen truncation risk. Lower output limits may
   make malformed JSON more likely.

4. Do not sort chunks by chunk_id as a "fix"
   Chunks already originate in document order. If ordering breaks, find the real
   upstream cause.

5. Do not design for forward-going "unprofiled" data
   New ingests should use a named profile. Legacy records without domain_profile
   may use compatibility fallbacks, but unprofiled should not become a new
   intended state.

6. Do not build separate logic for CLI, GUI, API, and MCP
   Core behavior belongs in services. CLI, GUI, API, and MCP should be thin
   interfaces over the same service layer.

7. Marker remains decided against for now
   Docling has been adopted as the (now base-dependency, as of WP-34.1 --
   see item 9 below) structure-aware path. Marker remains out unless a
   specific need beats its dependency and operational cost.

8. Do not build a second domain profile yet (2026-07-27)
   Cybersecurity is architecturally meant to be the first domain, not the only one
   (docs/PRODUCT_PRD.md's PR-2 names hr_policy/safety/finance/acquisition as future
   candidates), but building a real second profile now isn't worth it: no source
   documents exist for any candidate domain, non-default profiles bypass Step C's
   cache entirely (every iteration is a full re-extraction, not a resumed one --
   see docs/PROFILES.md), and the one existing profile still has known genericity
   gaps (hardcoded cybersecurity vocabulary in evidence_service.py's synthesis
   prompt -- see Phase 32's WP-32.7). Revisit once Phase 32 proves the core is
   actually domain-neutral, not just documented as intending to be.

9. [SUPERSEDED — Phase 34, WP-34.1] `--layout-mode` default changed from `pymupdf` to `auto` (2026-07-28)
   Original decision (kept below for history): Docling gives structure-aware
   chunking (section hierarchy, breadcrumbs, skip_sections filtering) that
   pymupdf/pdfplumber can't -- came up because a real empty-source_ref example
   turned out to be from a document ingested via pymupdf, prompting the
   question of why docling wasn't the default already. Answer at the time: it's
   a real ~700MB dependency (torch), so it's kept as an optional extra
   (`pip install "reqbot[docling]"`) rather than a hard requirement -- "auto" is
   what lets ingest use it automatically when installed without forcing the
   weight on every install. Falls back to pymupdf per-document (logged as a
   warning, not silent) if docling isn't installed or errors on a specific PDF;
   `--layout-mode docling` explicitly still fails loudly instead of falling
   back. Standalone fix, not part of Phase 32. Considered, and rejected at the
   time: making docling a hard base dependency -- would add ~700MB to every
   install including CI, for a benefit ("auto" already delivers) that most
   deployments may not need.

   Superseded 2026-07-29 (WP-34.1, docs/PHASE34_REQUIREMENTS.md): the ~700MB
   weight tradeoff above was reconsidered given ReqBot's actual deployment
   context (IT admins standing it up on a real network, not a
   storage-constrained device) and the legacy path's own real cost (no section
   hierarchy, permitting/causing several WP-33.3 actionability failure modes).
   `--layout-mode` and the entire pymupdf/pdfplumber path were removed; docling
   is now a base dependency and the only ingestion backend. A docling failure
   is now an unconditional hard error, not a per-document fallback.

10. ReqBot stays a compliance research/verification tool, not an
    enterprise-architecture-design consultant (2026-07-29, ChatGPT strategy
    conversation + Claude follow-up; see
    reqbot-agent-docs/reqbot/references/ReqbotConvo.md)
    Explored and declined: generating reference architectures, technology
    stack recommendations, draft SSPs/network diagrams, or a "compliance
    compiler" that takes a description of a target environment and outputs a
    full build plan. That's solution synthesis and opinionated engineering
    advice -- a different, harder product, competing in a different market,
    and it drops ReqBot's actual differentiator (a curated, provenance-
    tracked requirement corpus) in favor of one nobody has validated demand
    for. Tyler's own read at the time: "I'm not sure the marketability for
    ...an AI consultant on enterprise architecture. I don't know who the
    heck would buy that." Stay close to the existing premise -- extensions
    of the corpus/relationship data (see ACTIVE BACKLOG items 26-29), not a
    pivot into architecture design. Revisit only with real evidence of
    demand, not just that it would be technically possible to build.
