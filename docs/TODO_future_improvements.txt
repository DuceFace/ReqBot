ReqBot Future Improvements and Experiment Backlog
================================================================

Purpose
----------------------------------------------------------------
This file is a parking lot for useful ideas that should not be lost.
It is not a phase tracker, release plan, or source of truth for current
implementation status.

Use this document for:

- good ideas that are out of scope for the current work package
- experiments worth trying before committing to a feature
- cleanup items that are real but not urgent
- decisions we do not want to re-debate without new evidence

When an item becomes active work, move the detailed requirements into the
appropriate phase or work-package document. Keep this file short enough that
it remains useful.


================================================================
ACTIVE BACKLOG
================================================================

1. Step C concurrency
   Explore a small worker pool for LLM extraction. This could reduce long ingest
   times, but it must be tested carefully because local Ollama/GPU setups may
   become unstable with concurrent generation requests.

   Experiment gate:
   - measurable ingest-time improvement
   - no increase in malformed or partial LLM output
   - graceful behavior on single-GPU machines

2. Streaming write in Step A
   For very large PDFs, write page records incrementally instead of buffering all
   pages in memory. Current documents do not appear to require this, but it is a
   useful scalability hardening item.

3. Ollama finish_reason / token metadata
   Investigate whether Ollama response metadata can detect truncation more
   reliably than JSON parse failure alone.

4. Remove duplicate profile vocabulary constants
   Step C and Step D.5 still keep module-level VALID_DOMAIN_TAGS and
   VALID_REQUIREMENT_TYPES constants that mirror profiles/cybersecurity.json.
   They remain useful for compatibility today, but they are a second source of
   truth. Consider deriving fallback defaults from core.profiles when the profile
   plumbing is stable enough.

5. Profile-based skip-section filtering — docling-only gap
   profiles/*.json's skip_sections field is consumed when the docling engine is
   used (pipeline/run_pipeline.py passes it into chunk_text.run_structure_aware,
   which filters via _should_skip_chunk/_should_skip_section). But the default
   chunking engine is still the legacy pymupdf path, which has no section
   hierarchy and no-ops on skip_sections (pipeline/chunk_text.py logs a warning
   and ignores the field). So skip-section filtering only applies when a caller
   explicitly opts into docling. Revisit once docling is closer to being the
   default engine, or if legacy chunking gains its own section awareness.

6. Optional LLM-backed audit question generation
   Phase 21 intentionally leaves audit_question blank. A future opt-in feature
   may use an LLM to generate human-friendly audit questions, but it must not be
   default behavior.

   Guardrails:
   - explicit user flag or UI toggle
   - source_quote remains primary
   - no invented obligations
   - blank is better than an unsupported rephrase
   - generated questions should be marked as generated text

7. MCP tool surface (Phase 26 active work — see docs/PHASE26_REQUIREMENTS.md; original idea archived at archive/FUTURE_MCP_IDEA.md)
   Expose ReqBot as a tool server so external assistants can query a self-hosted
   ReqBot instance.

   Useful first tools:
   - search requirements
   - trace requirement
   - list documents
   - generate checklist
   - build evidence pack

   Architecture rule: MCP must call the same service layer as CLI and GUI.

8. Runtime validation for frontend API responses
    TypeScript types only protect at compile time. Runtime validation could catch
    backend/frontend contract drift before it becomes confusing UI behavior.

    Candidate library: Zod.

    Revisit when:
    - API surface grows further
    - external clients consume the API
    - contract drift causes a real debugging issue

9. Evidence view configurable result depth
    EvidenceView currently calls the API with a fixed top_k value. Add a simple
    control when users need to tune evidence depth.

10. Evidence view expandable sources and context
    Evidence groups currently emphasize the representative requirement. The API
    also returns all sources per group and context_text. A future UI can expose
    "show more sources" and surrounding context per group.

11. Checklist assessor-note preservation on regeneration
    Running generate() for a document that was already exported and annotated
    will silently reset assessor_notes and status to their initial values
    ("" / "not-started"). Any assessor work done against the exported CSV or
    JSON is lost unless the user saved the file.

    A future enhancement should detect a prior checklist export for the same
    doc_key and merge assessor_notes and status back in by checklist_item_id
    before writing output. Deterministic IDs make this possible without
    requiring the user to manage filenames.

    Design constraint:
    - merge must be opt-in or clearly documented, not silent
    - IDs are stable across re-runs for the same requirement_id, so a
      re-ingested document that produces the same requirement_ids will
      correctly re-associate assessor notes

12. Validate document_ids filter in core/ask.py (Codex review, WP-26.3/PR #114)
    core/ask.py's retrieve() passes document_ids straight into a Qdrant MatchAny
    filter with no existence check against the actual corpus. A typo'd or stale
    document_id doesn't error -- it just produces an empty or reduced hit set,
    indistinguishable from a legitimate no-match search. This violates the
    Phase 26 architecture rule that invalid document keys must not be hidden as
    fake empty results (docs/PHASE26_REQUIREMENTS.md Section 4, rule 5).

    Pre-existing gap in core/ask.py / services/ask_service.py, not introduced by
    or unique to MCP -- the CLI and API share the exact same hole today. Fix
    belongs in the shared service layer so CLI, API, and MCP all benefit
    identically; do not patch this into mcp_server/server.py alone (would create
    an MCP-only behavior fork -- see guardrail #6 in docs/PHASE26_REQUIREMENTS.md
    and DECISIONS AND GUARDRAILS #6 below). Needs its own planned WP: validate
    requested document_ids against docs_service.list_docs()'s known doc_keys
    before querying, and decide the failure shape (hard error vs. a warning
    entry, matching the existing warnings field precedent in ask_service.ask()'s
    response) -- design questions deferred to that WP, not implicit here.


================================================================
RETRIEVAL EXPERIMENTS
================================================================

These are quality experiments, not guaranteed product work.

1. Reranker spike
   Add a local reranker stage after RRF fusion for precision improvement.

   Candidate approaches:
   - FlashRank for fast local reranking
   - cross-encoder for higher quality with more cost

   Gate:
   - Precision@5 improvement
   - no regression on known good queries
   - acceptable latency on target hardware

2. Multi-vector retrieval
   Index multiple semantic surfaces per requirement, such as description and
   source_quote, to improve recall across different query styles.

   Critical rule:
   Collapse to unique requirement_id before reranking or display so one
   requirement cannot crowd out the result set.

3. HyPE / hypothetical question indexing (separate from HyDE)
   Pre-generate likely user questions for each requirement at ingest time and
   index those as an additional retrieval surface.

   This may improve query-time recall, but it adds generated text to the index
   and should be clearly separated from source-grounded fields.

4. Corrective retrieval gate
   If retrieval confidence is weak, retry once with a targeted rewrite or
   alternate retrieval strategy, then surface a low-confidence warning if the
   result is still weak.

   Depends on having calibrated reranking or confidence signals.

DEPENDENCY / TOOLCHAIN BACKLOG
================================================================

1. Vite major upgrade
   Current main uses Vite 5.x. Dependabot has proposed a Vite 8.x upgrade.
   Treat this as a frontend toolchain migration, not a tiny dependency patch.

   Before merging:
   - confirm GitHub Actions Node version supports Vite 8
   - confirm local developer Node version guidance is current
   - run frontend build
   - verify @vitejs/plugin-react, TypeScript, Tailwind, and PostCSS integration

   Note:
   The original security concern involved the Vite dev server. ReqBot production
   static files served through reqbot serve are a different risk surface.

2. React Router maintenance updates
   Same-major React Router updates are generally lower risk than Vite major
   upgrades. Merge when CI passes unless release notes show a relevant behavior
   change.

3. Security scanning / code checks in CI
   Currently only GitHub's passive Dependabot alerts cover this repo (dependency
   CVEs from the manifest files, surfaced on the Security tab — no CI job runs
   against them). No SAST, no secret scanning, no code-scanning job alongside
   the existing pytest/ruff CI checks. Worth adding eventually: bandit (or
   equivalent) for Python, an ESLint security plugin for the frontend, and/or
   GitHub code scanning (CodeQL). Not urgent — no known exploited issue driving
   this — but real automated coverage should replace ad hoc vigilance
   eventually rather than staying deferred indefinitely.

4. requirements.txt vs. pyproject.toml drift (Codex review, WP-25.2)
   WP-25.2 moved rapidfuzz into pyproject.toml's reqbot[dev] extra, since its
   only consumer (eval/eval_harness.py) isn't reachable through any product
   surface — but requirements.txt still lists it as a runtime dependency.
   Acceptable for now since requirements.txt is the legacy/source-install path,
   not actively wrong, but Phase 25 should eventually decide requirements.txt's
   fate: kept in sync with pyproject.toml's extras split, explicitly demoted to
   a "legacy path, may drift" doc note, or removed outright. WP-25.4 has now
   retired the bundle system, so requirements.txt's only remaining reason to
   exist is as the documented legacy/source-development path (README.md) —
   the decision is still open, just no longer tied to the bundle system.


================================================================
BACKBURNER
================================================================

1. OSCAL output
   OSCAL is a NIST-standardized machine-readable format for compliance data.
   It may be useful for integration with tools such as Archer or ServiceNow.

   Keep on backburner until a concrete integration target exists. Do not make
   OSCAL the default checklist format.

2. OCR support
   Useful if low-text page detection proves scanned PDFs are common. This should
   be a separate design decision because OCR can add heavy dependencies and
   operational complexity.

3. Authentication / multi-user hosting
   ReqBot currently fits self-hosted and local/air-gapped use well. Auth and
   multi-user hosting should be planned only when there is a deployment target
   that needs it.


================================================================
DECISIONS AND GUARDRAILS
================================================================

1. Keep description and source_quote
   They serve different purposes. source_quote is provenance; description is a
   readable normalized summary.

2. Do not use deterministic requirement_id hashing as the only ID strategy
   Requirement IDs can be assigned during normalization. Checklist item IDs may
   be deterministic from requirement IDs.

3. Do not lower num_predict casually
   The extraction path has already seen truncation risk. Lower output limits may
   make malformed JSON more likely.

4. Do not sort chunks by chunk_id as a "fix"
   Chunks already originate in document order. If ordering breaks, find the real
   upstream cause.

5. Do not design for forward-going "unprofiled" data
   New ingests should use a named profile. Legacy records without domain_profile
   may use compatibility fallbacks, but unprofiled should not become a new
   intended state.

6. Do not build separate logic for CLI, GUI, API, and MCP
   Core behavior belongs in services. CLI, GUI, API, and MCP should be thin
   interfaces over the same service layer.

7. Marker remains decided against for now
   Docling has been adopted as an optional structure-aware path. Marker remains
   out unless a specific need beats its dependency and operational cost.
